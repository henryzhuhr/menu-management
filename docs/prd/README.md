# PRD README

本目录维护菜单管理系统的项目级产品需求文档（PRD）。

这里的 PRD 不是“一需求一文档”的离散集合，而是一个随项目持续演进的需求体系。新增需求、规则变化、流程调整、范围收缩或扩展时，应优先更新现有章节；当内容规模变大时，再按模块拆分子文档，并保持本文件作为总索引。

## 1. 文档目标

本 PRD 用于回答以下问题：

- 这个项目要解决什么业务问题
- 当前产品范围包含什么，不包含什么
- 谁在使用系统，分别在什么场景下使用
- 各模块的核心业务规则、流程和边界条件是什么
- 如何判断一个需求是否完成验收

## 2. 维护原则

- 单一事实源：产品需求统一沉淀在本目录，不在聊天记录、临时文档或 issue 评论中长期存放关键信息。
- 持续演进：新增需求时优先修改已有章节，不默认新建一份独立 PRD。
- 模块化拆分：当某一主题内容过大时，可拆到子文档，但本文件必须保留索引和摘要。
- 面向协作：内容应能让新加入的产品、开发、测试、AI 助手快速理解项目全貌和当前范围。
- 可验收：每个重要模块都应明确验收标准，而不是只有模糊描述。

## 3. 当前产品范围

当前项目是一个菜单管理系统。以下范围为建议的第一层结构，后续可按实际项目推进调整。

### 3.1 核心模块

- 菜单基础信息管理
- 菜单分类管理
- 菜单项管理
- 菜单上下架与状态流转
- 菜单排序与展示规则
- 搜索与筛选
- 权限与角色控制
- 操作审计与变更记录

### 3.2 非功能目标

- 支持前后端分离协作
- 提供明确的接口契约与错误反馈
- 保证核心操作具备可审计性
- 保证菜单查询和管理操作具备可接受性能
- 为后续扩展门店、租户、多语言、多端展示预留空间

## 5. 建议章节模板

后续无论是写在本文件还是拆到子文档，建议每个模块至少包含以下结构：

### 5.1 背景与目标

- 为什么要做这个模块
- 解决什么业务问题
- 本阶段目标是什么

### 5.2 用户与场景

- 谁会使用这个能力
- 在什么场景下使用
- 使用频率、关键路径、前置条件是什么

### 5.3 功能范围

- 本次包含什么
- 本次明确不包含什么
- 与其他模块的边界是什么

### 5.4 业务规则

- 核心字段和定义
- 状态机或生命周期
- 排序、过滤、展示规则
- 权限控制规则
- 异常与边界处理规则

### 5.5 交互/流程

- 页面主流程
- 关键操作流程
- 异常流程

### 5.6 非功能性要求

- 性能要求
- 安全要求
- 审计要求
- 兼容性要求
- 可用性要求

### 5.7 验收标准

- 正常流程验收项
- 边界条件验收项
- 权限验收项
- 回归影响点

## 7. 变更规则

- 新需求进入时，先判断属于现有哪个模块或流程，再更新对应章节。
- 如果需求跨多个模块，应先更新总览中的范围说明，再分别更新相关模块章节。
- 如果需求改变现有规则，必须显式说明原规则、变更后规则和兼容影响。
- 如果某项需求暂不实现，应在文档中明确记录“本期不包含”而不是省略不写。
