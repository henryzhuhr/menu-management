# 发布通道决策

<a id="d061-channel-model"></a>
## D061 发布通道模型

- 提问：多个业务（应用）共用菜单中心，各应用下的租户需要以不同节奏接收菜单版本，应该如何设计版本发布机制？
- 提问解释：支付业务、电商业务等是独立应用，每个应用下有多租户。租户按升级协议分为不同等级——KA 用户只接受经过完整验证的版本，STD 用户接受中间验证后的版本，EAP 用户愿意最早尝鲜。需要确定版本如何组织和分发。
- 用户决策：三级发布通道（Release Channel）——EAP → STD → KA，应用级独立维护。
- 需求影响：
  - 系统需要支持 EAP、STD、KA 三个发布通道，通道为应用级（每个应用独立维护通道）。
  - 通道控制的是**版本推出的时间节奏**，而非版本内的功能可见性。同一版本在各通道中的内容完全一致，不同通道只是在不同时间点指向该版本。
  - 版本创建默认从 EAP 通道开始，紧急或低风险变更允许跳过直达 STD 或 KA。
  - 版本沿通道逐级推进：EAP 验证通过后推进到 STD，STD 验证通过后推进到 KA。前一个版本必须完成全通道推进（EAP → STD → KA，即全量发布），才能创建下一个新版本。
  - 版本号跨通道一致：同一版本号在各通道中指向相同内容。

<a id="d062-tenant-channel-binding"></a>
## D062 租户通道绑定

- 提问：租户如何确定自己属于哪个通道？是否允许例外情况？
- 提问解释：租户按升级协议打标签，但可能存在平台需要临时给特定租户覆盖版本的场景。
- 用户决策：通道绑定 + 例外覆盖。
- 需求影响：
  - 每个租户绑定一个默认通道（EAP / STD / KA），租户命名示例：`Tenant-EAP_01`、`Tenant-STD_01`、`Tenant-KA_01`。
  - 平台管理员可以给特定租户设置版本例外覆盖，临时让租户看到非所属通道的版本。
  - 例外覆盖需要记录审计。

<a id="d063-security-hotfix"></a>
## D063 安全变更处理

- 提问：安全相关的菜单变更（权限撤销、菜单下线等）是否需要走 EAP → STD → KA 逐级推进？
- 提问解释：[D028](../decisions/005-release-governance.md#d028-realtime-scope) 已确定安全变更需要实时生效，与发布通道模型结合时需要特殊处理。
- 用户决策：安全变更走 hotfix，全员即时生效。
- 需求影响：
  - 安全变更可跨通道直达所有租户，不需要逐级推进。
  - 安全 hotfix 本身需要记录为特殊版本变更，产生审计记录。

<a id="d064-cross-channel-preview"></a>
## D064 跨通道预览

- 提问：租户或管理员是否需要预览其他通道的菜单效果？
- 提问解释：EAP 租户可能需要验证"KA 通道看到的是什么"；被例外覆盖的租户可能需要预览自己原本通道的版本；平台管理员发布前需要验证"推到 STD 通道后 STD 租户看到什么"。
- 用户决策：预览 + 模拟切换 + 沙箱体验。
- 需求影响：
  - 预览支持以指定租户 + 指定通道的视角查询菜单，纯查询不影响任何状态。
  - 租户可模拟切换到其他通道进行沙箱体验，在一定时间内以模拟模式使用，正式环境仍走原本通道。

<a id="d065-version-snapshot"></a>
## D065 版本创建与功能上车

- 提问：版本如何创建？功能如何上车？
- 提问解释：管理员需要基于当前版本创建新版本，并对菜单功能进行增删改。
- 用户决策：基于快照的增量编辑（方式 A），版本由平台管理员创建。
- 需求影响：
  - 管理员基于当前最新版本（通常是 KA 通道的已全量版本）的快照，进行功能的增删改后保存为新版本。
  - 新版本默认发布到 EAP 通道，EAP 服务实例通过 version 配置指向新版本号。
  - 版本推进通过更改各通道服务实例的 version 配置实现：STD 服务指向新版本号即 STD 推进完成，KA 服务指向新版本号即全量发布完成。
  - 前一个版本全通道推进完成后，才能创建下一个新版本。不支持多版本并行在通道间推进。

<a id="d066-db-snapshot-storage"></a>
## D066 数据库存储模型

- 提问：菜单数据在数据库中如何按版本存储？
- 提问解释：三个通道的服务实例共享同一数据库，每个服务实例通过 version 配置知道自己查询哪个版本。需要确定存储粒度。
- 用户决策：每版本完整快照 + 按应用独立存储。
- 需求影响：
  - 每个应用有独立的版本线，数据库中以 `(app, version)` 组合隔离。
  - 支付 v5 的创建不影响电商 v2，双方数据零耦合。
  - 不需要 `stability` 字段，管理员在创建新版本时自行判断功能增减。

<a id="d067-service-version-mapping"></a>
## D067 服务实例的版本映射

- 提问：一个通道的服务实例只有一个 version 配置，但各应用的版本进度不同，如何处理？
- 提问解释：STD 通道下，支付当前是 v5，电商是 v2，STD 服务需要同时为订阅了支付+电商的租户提供正确菜单。
- 用户决策：服务实例使用应用-版本映射配置（方案 A）。
- 需求影响：
  - 每个通道的服务实例不再配置单一 version，改为配置 `{app → version}` 映射。
  - STD 服务配置：`{支付: v5, 电商: v2}`，查询时按 app + version 组合查询。
  - 每个应用独立推进自己的版本，互不影响。支付创建新版本不动电商数据，回滚也不影响电商。
  - 实现了"业务独立发布、互不影响"的要求。
