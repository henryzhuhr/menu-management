3. 核心问题：多应用 + 单服务实例

graph TB subgraph SCENE["场景：Tenant-STD_01 查询菜单"] T["Tenant-STD_01
订阅了：支付 + 电商"] end subgraph SVC["STD Namespace 的菜单服务"] S["菜单服务
version = ???"] end subgraph DATA["数据库中的版本快照"] D1["支付 v6（EAP 通道）"] D2["支付 v5（STD 通道）"] D3["支付 v4（KA 通道）"] D4["电商 v2（全部通道）"] end T -->|"GET /menu?tenant=STD_01"| S S -->|"SELECT * FROM menu_items
WHERE version=? AND app=?"| DATA style S fill:#ff6b6b,color:#fff

问题：STD 服务只有一个 version 值，但支付（v5）和电商（v2）的 STD 通道版本不同。
如果 version=v5 → 电商查不到菜单；如果 version='v2' → 支付拿到旧版本。

4. 方案 A：version 按应用映射

graph LR subgraph SVC_A["STD 服务实例"] CFG["version 配置改为映射
支付 → v5
电商 → v2"] end subgraph DB_A["数据库"] Q1["WHERE app='支付' AND version='v5'"] Q2["WHERE app='电商' AND version='v2'"] end CFG --> Q1 CFG --> Q2

每个应用的版本独立推进，服务按应用 + 版本组合查询。灵活但配置复杂度随应用数增长。

5. 方案 B：全局版本号聚合

graph LR subgraph SVC_B["STD 服务实例"] CFG2["version = v6（全局）"] end subgraph DB_B["数据库"] Q3["WHERE version='v6'
支付(新内容) + 电商(自动拷贝)"] end CFG2 --> Q3

version 号全局递增。v6 只改了支付，电商内容自动从 v5 拷贝。查询简单但每次发版都需要聚合所有应用快照。
