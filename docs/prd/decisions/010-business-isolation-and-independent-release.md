# 业务隔离与独立升级决策

<a id="d068-business-release-unit"></a>
## D068 业务是菜单发布的最小独立单元

- 提问：多个业务共用菜单中心时，菜单版本是否需要一起升级？
- 提问解释：业务 A 和业务 B 共用一个菜单模块，但 A 希望独立发布菜单变更，不影响 B，需要明确版本和发布的隔离边界。
- 用户决策：菜单配置以业务（应用）为最小发布单元；菜单服务可以共享，但菜单版本、通道指针、灰度规则、回滚范围必须按应用隔离。
- 需求影响：
  - 所有菜单版本使用 `(app, version)` 作为业务范围。
  - 每个应用独立维护 EAP、STD、KA 通道指针。
  - 业务 A 创建、灰度、发布或回滚菜单版本时，不得改变业务 B 的菜单版本指针。
  - 同一个菜单服务可以通过 `app` 上下文同时返回多个业务的菜单。

<a id="d069-runtime-code-release-boundary"></a>
## D069 菜单配置发布与模块代码发布解耦

- 提问：业务 A 希望升级独立于业务 B，是否意味着菜单模块代码也必须分别部署？
- 提问解释：菜单内容版本和菜单服务本身的代码版本影响范围不同，必须分别定义发布规则。
- 用户决策：两类发布分开治理。
- 需求影响：
  - 菜单配置发布属于应用级发布，支持业务级灰度、全量和回滚。
  - 菜单服务代码发布属于运行时部署级发布。共享运行实例时，代码发布会影响该实例承载的所有业务。
  - 共享运行实例中的新代码必须保持向后兼容，并通过应用级 feature flag 控制新能力是否启用。
  - 业务确实需要代码独立升级时，为该业务分配独立运行组或服务实例；运行组使用同一菜单服务代码和控制面，但可以独立选择代码镜像版本。
  - 数据库迁移必须遵循先扩展、再切换、后收缩，保证新旧代码在过渡期可以同时工作。

<a id="d070-menu-runtime-context"></a>
## D070 运行时菜单必须携带业务上下文

- 提问：一个菜单服务如何同时提供业务 A 和业务 B 的菜单？
- 提问解释：仅凭租户和用户无法确定菜单归属，尤其是一个租户可能同时订阅多个业务。
- 用户决策：运行时请求必须包含受信任的 `app` 上下文，并与租户、用户、环境、地域和客户端一起参与菜单解析。
- 需求影响：
  - 菜单查询的逻辑上下文为 `(app, tenant, user, environment, region, client, locale)`。
  - `app` 优先来自访问令牌、网关路由或服务端调用上下文，不能只信任前端任意传入的查询参数。
  - 业务 A 和业务 B 即使共享同一服务实例，也必须查询各自的版本快照和发布指针。
  - 需要支持按应用进行权限校验、诊断、审计、缓存隔离和指标统计。

<a id="d071-gray-resolution"></a>
## D071 灰度版本选择规则

- 提问：业务 A 的新版本如何只对部分租户或用户生效？
- 提问解释：业务级独立发布解决了 A 与 B 的边界，但还需要确定同一业务内部的版本命中顺序。
- 用户决策：灰度只在目标应用内部生效，版本选择按固定优先级解析。
- 需求影响：
  - 版本命中优先级为：安全 hotfix > 应用级租户版本例外 > 灰度规则 > 应用-通道指针。
  - 灰度规则至少支持租户、环境和地域；用户白名单、客户端和比例灰度作为可扩展维度。
  - 没有命中业务 A 灰度规则的租户继续使用 A 当前通道版本；业务 B 不参与 A 的规则计算。
  - 每次运行时响应需要能追溯命中的应用、版本、通道或灰度规则，诊断接口返回完整命中链路。
