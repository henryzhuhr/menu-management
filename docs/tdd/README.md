# TDD README

本目录维护项目的设计文档。

这里也采用持续更新的方式，不是一需求一份文档。只记录当前开发真正需要的设计结论，不写过重的流程材料。

## 目标

TDD 只需要回答几个最基本的问题：

- 准备怎么做
- 技术栈和工具怎么选
- 涉及哪些模块
- 接口和数据怎么定
- 有没有特别需要注意的约束
- 需要怎么测试

## 建议写法

如果是一个新功能，通常补这几项就够了：

- 方案概述
- 技术选型
- 模块边界
- 接口设计
- 数据设计
- 测试方式

## TDD 参考清单

每次编写 TDD 时，默认参考以下清单，不要求机械地全部写满，但应按这份清单检查是否需要覆盖。

- 问题定义与目标
- 总体方案与备选方案对比
- 系统边界与模块职责
- 数据模型、表结构、索引、缓存策略
- 后端接口设计：路由、请求、响应、错误码、鉴权
- 前端页面/组件设计、状态流转、交互约束
- 关键业务流程时序
- 可观测性设计：日志、指标、追踪、审计
- 测试方案：单元测试、集成测试、端到端测试、回归测试
- 发布方案、回滚方案、数据迁移方案

可以按以下方式使用这份清单：

- 小改动：只写与本次改动直接相关的项
- 中等改动：补齐方案、模块、接口、数据、测试等关键项
- 较大改动：尽量完整覆盖清单中的主要项

## 高风险变更约束

如果本次改动涉及以下内容，TDD 中必须单列说明风险和处理方式：

- 数据库
- 缓存
- 消息
- 权限
- 安全策略

这类改动至少应补清楚：

- 影响范围
- 风险点
- 兼容方式
- 测试方式
- 必要时的回退思路

## 维护规则

- 优先更新现有文档，不默认新建新文件
- 设计写到“足够开始开发”即可
- 如果实现改了设计，顺手把文档同步掉
