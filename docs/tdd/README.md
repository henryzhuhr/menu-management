# TDD README

本目录维护菜单管理系统的项目级技术设计文档（TDD）。

这里的 TDD 不是“一需求一文档”的离散集合，而是一个随项目持续演进的设计体系。随着需求、架构、接口、数据模型和运维策略变化，应持续更新现有设计内容；当内容规模增大时，再按模块或技术专题拆分子文档，并保持本文件作为总索引。

## 1. 文档目标

本 TDD 用于回答以下问题：

- 系统整体如何分层与协作
- 各模块分别如何实现
- 数据模型、接口契约、缓存策略如何定义
- 如何保证系统的可维护性、可测试性、可观测性和可发布性
- 当前设计有哪些约束、风险和后续演进方向

## 2. 维护原则

- 单一事实源：技术设计统一沉淀在本目录，避免关键信息散落在聊天记录、代码注释或临时草稿中。
- 持续演进：需求变化时优先更新现有设计章节，而不是默认新建一份独立 TDD。
- 与实现对齐：TDD 不是空谈文档，必须与当前代码结构、接口、数据结构保持同步。
- 关注权衡：设计不仅记录“怎么做”，也要说明“为什么这样做”以及放弃了哪些方案。
- 可交付：设计中应包含测试、发布、回滚、风险控制等工程信息，而不是只有模块说明。

## 3. 当前技术基线

根据仓库约定，当前技术栈如下：

- 后端：Golang + Gin
- 前端：Vue3 + TypeScript
- 数据库：PostgreSQL
- 缓存：Redis
- 自动化测试：Python + `uv` + `pytest`
- UI 自动化验证：`agent-browser`
- 部署与依赖：Docker Compose

## 5. 建议章节模板

后续无论写在本文件还是拆到子文档，建议每个技术专题至少包含以下结构：

### 5.1 问题定义

- 要支撑哪个产品能力
- 当前要解决什么实现问题
- 输入输出边界是什么

### 5.2 方案概述

- 核心设计思路
- 模块划分
- 数据流与控制流

### 5.3 备选方案与权衡

- 有哪些备选实现
- 为什么选择当前方案
- 当前方案的限制是什么

### 5.4 详细设计

- 后端模块职责
- 前端模块职责
- API 契约
- 数据模型
- 缓存设计
- 错误处理
- 权限控制

### 5.5 可观测性与运维

- 日志策略
- 指标与告警
- 审计记录
- 配置项
- 发布顺序
- 回滚策略

### 5.6 测试设计

- 单元测试范围
- 集成测试范围
- 端到端测试范围
- 关键回归点

### 5.7 风险与待定事项

- 已知技术风险
- 未决策问题
- 后续优化方向

5. 前端页面结构和状态流转设计

## 7. 设计更新规则

- 需求变化时，先更新对应设计章节，再进行实现或同步实现变更。
- 涉及接口变更时，必须同步更新接口设计说明。
- 涉及数据结构变更时，必须同步更新数据库/缓存设计及迁移策略。
- 涉及权限、安全、审计变更时，必须在设计中明确风险与控制手段。
- 如果代码实现临时偏离设计，后续必须尽快统一；不允许长期“代码一套、文档一套”。
