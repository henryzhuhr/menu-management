# 总体架构

本设计将菜单配置发布和菜单服务代码发布拆开，保证同一菜单服务可以服务多个业务，同时支持业务级灰度和必要时的代码独立升级。

## 1. 方案概述

采用“统一控制面 + 可共享或隔离的数据面”模型：

- 控制面统一维护应用、菜单快照、发布通道、灰度规则、租户绑定、审批和审计。
- 数据面提供运行时菜单查询。默认按 EAP、STD、KA 运行组共享服务实例；每个运行组维护 `{app -> version}` 映射。
- 菜单版本按应用保存完整快照。运行时先根据业务上下文选出 `(app, version)`，再执行权限、订阅、环境、地域和客户端过滤。
- 菜单服务代码默认共享发布，通过向后兼容和应用级 feature flag 控制新能力；需要业务 A 代码独立升级时，为 A 分配独立运行组。

## 2. 技术选型

- 对外使用 HTTP/JSON 运行时接口，管理面接口和运行时接口分离。
- 使用支持事务和唯一约束的关系型数据库保存应用、版本快照、发布指针和审计记录。
- 缓存只缓存最终解析结果或应用-版本快照，缓存 key 必须包含 `app`、租户、环境、地域、客户端和用户权限上下文。
- 具体语言、框架和部署编排工具在工程初始化时确定，本阶段不影响上述边界。

## 3. 模块

- 应用与租户上下文：校验应用、租户和调用方的归属关系。
- 菜单配置：维护逻辑菜单、客户端展示元数据和应用内版本快照。
- 发布治理：维护通道指针、灰度规则、版本例外、审批、回滚和审计。
- 运行时解析：按上下文选版本，执行安全优先的可见性计算并返回导航元数据。
- 运行组配置：维护运行组承载的应用范围、代码镜像版本和应用 feature flag。
- 诊断与指标：解释版本命中和菜单隐藏原因，并按应用统计请求、命中版本和错误。

## 4. 接口与数据

运行时核心接口：

```text
GET /v1/apps/{app}/menu
```

请求上下文至少包括 `tenant`、`user`、`environment`、`region`、`client` 和 `locale`；`app` 必须经过令牌、网关或服务端调用校验。可提供批量接口，但批量结果仍按应用独立返回。

版本解析顺序：

```text
hotfix -> tenant version override -> gray rule -> app/channel pointer
```

建议的数据结构：

| 数据 | 关键字段 | 约束 |
|------|----------|------|
| `app` | `id`, `code`, `status` | `code` 唯一 |
| `menu_version` | `app_id`, `version`, `base_version`, `content_hash`, `status` | `(app_id, version)` 唯一，快照不可变 |
| `channel_pointer` | `app_id`, `channel`, `environment`, `region`, `version` | 同一作用域只有一个生效指针 |
| `gray_rule` | `app_id`, `target_version`, `conditions`, `priority`, `status` | 只能作用于所属应用 |
| `tenant_version_override` | `app_id`, `tenant_id`, `version`, `expires_at` | 需要审计和过期处理 |
| `runtime_group` | `group_id`, `channel`, `environment`, `image_version` | 运行组可承载多个应用 |
| `app_runtime_binding` | `app_id`, `runtime_group_id`, `effective_at` | 需要代码独立升级时，将应用绑定到独立运行组 |
| `app_feature_flag` | `app_id`, `key`, `value`, `target_scope` | 不得绕过权限和订阅校验 |
| `audit_event` | `app_id`, `operation`, `actor`, `target`, `before`, `after` | 发布、灰度、回滚必须记录 |

## 5. 约束

- 应用是版本、发布、回滚、缓存和诊断的基本隔离边界。
- 菜单版本使用完整快照，发布只切换指针，不原地修改已发布快照。
- 共享实例代码升级不等于所有业务启用新能力；必须使用向后兼容和 feature flag。
- 代码独立升级采用独立运行组，不复制一套菜单数据模型或控制面。
- 数据库变更采用扩展、双读/双写（必要时）、切换、收缩的兼容迁移顺序。
- `app`、`tenant`、`user` 的关系必须在服务端校验，不能只靠客户端参数。
- 热修复可以跨通道即时生效，但必须保留审计和回滚信息。

## 6. 测试

- 业务隔离：A 发布、灰度、回滚时，B 的版本指针、响应和缓存不变。
- 多业务查询：同一运行实例分别查询 A、B，返回对应快照；同一租户订阅多个业务时不能串菜单。
- 灰度命中：验证通道指针、灰度规则、租户例外和 hotfix 的优先级与边界。
- 代码兼容：旧代码读取新数据、新代码读取旧数据，验证迁移过渡期均可用。
- 独立运行组：A 升级代码镜像时，B 继续由旧运行组提供服务。
- 安全性：伪造或替换 `app` 参数不能跨业务读取菜单或权限结果。
- 使用 `agent-browser` 做页面验证与关键交互测试，使用 Playwright 做端到端发布链路测试。

## 7. 备注

- 首期建议先实现应用级菜单配置独立发布和灰度；独立运行组作为需要代码隔离时的部署能力，不作为所有业务的默认成本。
- 仍需在工程阶段确认运行组配置由平台自动发布还是由部署平台执行，以及 feature flag 的具体存储方式。
